#+TITLE: What chez-httparse v0.1 does, and what it does not
#+OPTIONS: toc:2

The claim this project makes is narrow and checkable: *strict-mode HTTP/1.x
request and response parsing, byte-exact against llhttp's own recorded
traces, for 190 of the 253 HTTP fixtures in its conformance corpus.* The
other 63, plus 21 URL fixtures, are enumerated below rather than omitted.

A compatibility claim that names what it does not do is the only kind worth
publishing.

* How conformance is measured

llhttp's test corpus is not a list of inputs — each fixture carries the exact
trace llhttp's own instrumented parser prints for it, offset by offset:

#+begin_example
off=0 message begin
off=0 len=7 span[method]="OPTIONS"
off=7 method complete
...
off=60 headers complete method=6 v=1/1 flags=0 content_length=0
#+end_example

The corpus is vendored verbatim from llhttp =v9.4.3-1-gee51043=, checksummed,
and never edited. Every in-scope fixture is replayed *at every chunk size
from 1 to its length* and the parser's rendered trace is compared byte for
byte. That is where resumability is tested: a parser that mishandled a token
split across feeds would produce a different trace at some size.

Two executors run the same fixtures and must agree — the committed generated
parser and a reference interpreter built from the grammar — so a code
generator that emitted something wrong-but-well-formed does not pass.

The result is a *ratchet*: a manifest naming every fixture and its status. It
fails both when a passing fixture breaks and when a deferred one starts
passing, so a change in either direction is a reviewed diff.

* The 84 not in v0.1

| Deferred            | Fixtures | Why                                                |
|---------------------+----------+----------------------------------------------------|
| Lenient modes       |       37 | v0.1 is strict only                                |
| Pausing and upgrade |       24 | control flow, not HTTP; the machinery exists       |
| URL sub-parser      |       21 | =url.md= only; the target is one opaque span here  |
| =skipBody=          |        2 | an embedder instruction v0.1 does not offer        |

Each is a milestone of its own, and every one of their fixtures is already
vendored and already in the ratchet — so the deferral is a visible count
rather than an absence, and the day one is picked up its corpus is present,
checksummed, and failing for the right reason.

* Divergences from llhttp, measured

A live llhttp binary, built from the same commit the corpus came from, is
run against generated input that the corpus does not contain — messages
assembled from a grammar and mutants of real fixtures. Over ~110,000
comparisons across four seeds, every disagreement falls into one of the
following, and an unclassified one fails the lane.

** The request target is one opaque span

llhttp runs a URL sub-parser over the request target and rejects targets
whose *structure* is wrong. This parser carries the target as a single span,
as every =uri.md= fixture is written against, and reads on where llhttp
stops.

#+begin_example
OPTIONS a.com:443 HTTP/1.1

llhttp: off=9 error code=7 reason="Unexpected char in url schema"
ours:   parses to completion
#+end_example

This is the deferred URL sub-parser, and it is the largest of the three by a
wide margin.

** A completion event at the exact end of the input

Two mirrored cases, both visible *only* when a feed ends exactly at a token
boundary — which no recorded fixture does, because every one of them has a
byte after the token.

- *One event short.* llhttp fires a keyword's completion on the keyword's
  last byte. The state-machine generator's keyword table reports
  =need-input= there and takes the terminal edge only when a further byte
  arrives.

  #+begin_example
  input "HTTP" (a response, 4 bytes, whole buffer)

  llhttp: ... off=4 protocol complete
  ours:   ... (nothing)
  #+end_example

- *One event too many.* Where a completion fires one byte *past* its
  delimiter — =url complete=, =header_field complete= — llhttp needs that
  byte to be present and this parser does not.

  #+begin_example
  input "PUT /url " (9 bytes, whole buffer)

  llhttp: ... off=4 len=4 span[url]="/url"
  ours:   ... off=4 len=4 span[url]="/url" / off=9 url complete
  #+end_example

One more byte in either case and the two agree exactly. The first is an
upstream gap with a brief filed against it; the second is a modelling
difference.

* A property that is true only with its qualifier

A resumable parser is expected to produce the same trace however the bytes
arrive. *That holds for a parse that reaches no error* — measured over
generated input, 71 of 71 error-free cases were invariant across chunk
sizes — and it is false for 13 of 169 that error.

The cause is that a span still open when the parse fails is printed only for
the bytes a chunk boundary already flushed:

#+begin_example
ICE/2.0 102 OK / Upgrade:websocket / Trailer : X-T     (a token error)

whole buffer: ... header_value complete / error
one byte:     ... header_value complete /
              off=35 len=7 span[header_field]="Trailer" / error
#+end_example

llhttp does exactly the same thing. The unqualified property would have been
a false one, and the corpus could not have said so, because upstream chose
fixtures the qualifier holds for.

* Things found this way

The live differential is not decoration. Building it turned up three defects
the 190-fixture corpus could not see, all now fixed and pinned by offline
checks:

1. =message begin= was withheld when the first byte was one no method may
   start with. No fixture begins with such a byte.
2. Repeated spaces between the method and the target produced an *empty*
   target span. llhttp requires one space and skips the rest; so does this
   parser now, before the target and before the protocol.
3. The two RTSP methods were spelled =GET-PARAMETER= and =SET-PARAMETER=.
   llhttp's map keys them =GET_PARAMETER= and =SET_PARAMETER= — underscores,
   as RFC 2326 spells them — and only ='M-SEARCH'= is quoted and
   hyphenated. Six milestones of a wrong name that no fixture uses.

* Running it yourself

The differential is local and opt-in, never a merge gate: llhttp's own test
harness needs Node and a C toolchain, and the evidence CI needs is already
checked in.

#+begin_src sh
git clone https://github.com/nodejs/llhttp ~/src/llhttp
cd ~/src/llhttp && git checkout v9.4.3 && npm install
cd - && cmake --preset dev -DHTTPARSE_LLHTTP_ROOT=$HOME/src/llhttp
ctest --preset pr -R differential
#+end_src

Without that variable the lane is *absent* — not skipped, not failing, not
registered at all.
