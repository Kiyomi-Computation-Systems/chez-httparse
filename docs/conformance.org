#+TITLE: What chez-httparse does, and what it does not
#+OPTIONS: toc:2

The claim this project makes is narrow and checkable: *HTTP/1.x request and
response parsing, byte-exact against llhttp's own recorded traces, for* all
274 *fixtures in its conformance corpus — every HTTP fixture and every URL
fixture it ships, at every chunk size.*

v0.1 shipped 190 of them, strict-mode only. Pausing and =skipBody= (26) came
in after it, then the eleven lenient flags (37), then the url sub-parser (21).
All of that is on =main=, unreleased.

Strict is still the *default* and lenient is still opt-in; what changed since
is only how you ask. The eleven flags are a bitset you hand =make-parser=,
not eleven callbacks it asks you — see [[file:api.org][api.org]].

*The 21 URL fixtures are a SECOND PARSER, and they pass.* They were listed
here as out of scope until M11; what they exercise is
=(generated httparse-url)=, whose five separate spans exist only in llhttp's
own url binary. The HTTP parser's request-target is still one =span[url]=.

A compatibility claim that names what it does not do is the only kind worth
publishing.

* How conformance is measured

llhttp's test corpus is not a list of inputs — each fixture carries the exact
trace llhttp's own instrumented parser prints for it, offset by offset:

#+begin_example
off=0 message begin
off=0 len=7 span[method]="OPTIONS"
off=7 method complete
...
off=60 headers complete method=6 v=1/1 flags=0 content_length=0
#+end_example

The corpus is vendored verbatim from llhttp =v9.4.3-1-gee51043=, checksummed,
and never edited. Every in-scope fixture is replayed *at every chunk size
from 1 to its length* and the parser's rendered trace is compared byte for
byte. That is where resumability is tested: a parser that mishandled a token
split across feeds would produce a different trace at some size.

Two executors run the same fixtures and must agree — the committed generated
parser and a reference interpreter built from the grammar — so a code
generator that emitted something wrong-but-well-formed does not pass.

The result is a *ratchet*: a manifest naming every fixture and its status. It
fails both when a passing fixture breaks and when a deferred one starts
passing, so a change in either direction is a reviewed diff.

* Nothing is out

Every fixture the corpus ships is gated and passing: *274 of 274*. The
deferral column that stood here through eleven milestones is empty, and the
ratchet asserts the emptiness as a number rather than by no longer having a
row.

*That is a statement about FIXTURES, not about every difference from llhttp.*
The measured divergences below are found by generated input the corpus does
not contain. There were three; *the largest is now closed*, and the two that
remain are the same narrow case seen from both sides.

* Divergences from llhttp, measured

A live llhttp binary, built from the same commit the corpus came from, is
run against generated input that the corpus does not contain — messages
assembled from a grammar and mutants of real fixtures. Over ~110,000
comparisons across four seeds, every disagreement falls into one of the
following, and an unclassified one fails the lane.

** Closed: the request target is now parsed, not carried

This was the largest of the three — *45 comparisons* — and it is gone.

#+begin_example
OPTIONS a.com:443 HTTP/1.1

llhttp: off=9 error code=7 reason="Unexpected char in url schema"
ours:   off=9 error code=7 reason="Unexpected char in url schema"
#+end_example

llhttp runs a URL sub-parser over the request target and rejects targets
whose *structure* is wrong. This parser carried the target as a single span
and read on. Since the sub-parser was spliced into the request-target path,
it does not: =agreed= went 1097 → 1142, every one of the 45 became an
agreement, and the class was deleted rather than left at zero.

*The target is still ONE =span[url]=*, which is what every =uri.md= fixture
is written against. llhttp builds the same machine two ways — five separate
spans for its =url= binary, one whole span inside the HTTP parser — and so
does this.

*This made the parser stricter.* A target that used to parse may now be an
error. That is llhttp's behaviour, arrived at deliberately; see
[[file:api.org][api.org]].

** A completion event at the exact end of the input

Two mirrored cases, both visible *only* when a feed ends exactly at a token
boundary — which no recorded fixture does, because every one of them has a
byte after the token.

- *One event short.* llhttp fires a keyword's completion on the keyword's
  last byte. The state-machine generator's keyword table reports
  =need-input= there and takes the terminal edge only when a further byte
  arrives.

  #+begin_example
  input "HTTP" (a response, 4 bytes, whole buffer)

  llhttp: ... off=4 protocol complete
  ours:   ... (nothing)
  #+end_example

- *One event too many.* Where a completion fires one byte *past* its
  delimiter — =url complete=, =header_field complete= — llhttp needs that
  byte to be present and this parser does not.

  #+begin_example
  input "PUT /url " (9 bytes, whole buffer)

  llhttp: ... off=4 len=4 span[url]="/url"
  ours:   ... off=4 len=4 span[url]="/url" / off=9 url complete
  #+end_example

One more byte in either case and the two agree exactly. The first is an
upstream gap with a brief filed against it; the second is a modelling
difference.

* A property that is true only with its qualifier

A resumable parser is expected to produce the same trace however the bytes
arrive. *That holds for a parse that reaches no error* — measured over
generated input, 71 of 71 error-free cases were invariant across chunk
sizes — and it is false for 13 of 169 that error.

The cause is that a span still open when the parse fails is printed only for
the bytes a chunk boundary already flushed:

#+begin_example
ICE/2.0 102 OK / Upgrade:websocket / Trailer : X-T     (a token error)

whole buffer: ... header_value complete / error
one byte:     ... header_value complete /
              off=35 len=7 span[header_field]="Trailer" / error
#+end_example

llhttp does exactly the same thing. The unqualified property would have been
a false one, and the corpus could not have said so, because upstream chose
fixtures the qualifier holds for.

* Things found this way

The live differential is not decoration. Building it turned up six defects
the corpus could not see, all now fixed and pinned by offline checks:

1. =message begin= was withheld when the first byte was one no method may
   start with. No fixture begins with such a byte.
2. Repeated spaces between the method and the target produced an *empty*
   target span. llhttp requires one space and skips the rest; so does this
   parser now, before the target and before the protocol.
3. The two RTSP methods were spelled =GET-PARAMETER= and =SET-PARAMETER=.
   llhttp's map keys them =GET_PARAMETER= and =SET_PARAMETER= — underscores,
   as RFC 2326 spells them — and only ='M-SEARCH'= is quoted and
   hyphenated. Six milestones of a wrong name that no fixture uses.
4. A host holding two =@= that are not adjacent was refused. llhttp accepts
   =http://a@b@c/p= and refuses only =a@@b=; =url.md='s "Double =@=" fixture
   has its two adjacent, so neither the corpus nor the oracle-measured cases
   could tell the two rules apart.
5. A bare LF after a request's version was accepted under
   =OPTIONAL_CR_BEFORE_LF= alone. llhttp needs *both* lf flags; with the
   first alone it still refuses, at the same offset and with the same reason,
   and a different code. Only a flag *pair* can see it.
6. A response status line with no reason phrase, ending in a bare LF, was
   refused. Upstream gates it on =OPTIONAL_CR_BEFORE_LF= and this parser had
   no fork there at all — a thirty-third lenient site where decision 0020's
   sweep measured thirty-two, because a fork that is not there is not a
   site.

* Both properties, both machines

The property lane needs no llhttp and runs on every pull request. It asks two
things of generated input — a parse that reaches no error produces the same
trace however the bytes arrive, and the shipped artifact agrees with the
interpreted grammar — and it asks both of *both* machines, the message parser
and the url sub-parser, each with its own artifact and its own twin.

Every floor in that lane is *per kind*. Both properties pass vacuously over a
run that selected nothing, so both are guarded by a floor; one floor over the
whole run is satisfied by the message kinds alone, whatever the url machine
contributes. `HTTPARSE_PROPERTY_URL_CASES=0` shows it: the global floor
passes, the per-kind ones fail.

=url.md='s =noScan= annotation is *checked, not quoted*. It marks that file's
four error fixtures; only three of them actually diverge across chunk sizes.
"Failing on broken schema" closes its schema span before the error, so no
chunk boundary has an open span to flush early — and llhttp does not diverge
on it either.

* Lenient flags, in combination

Upstream's fixture harness picks its init hook with a =-D= at compile time
and ships one per (kind, single flag). So a *pair* of flags cannot be asked
of it at all: 55 pairs would be 55 binaries, and no hook exists for any of
them. Its only combination fixtures are three =*-lenient-all= ones — and
=lenient_all= sets *nine of the eleven*, leaving =spaces-after-chunk-size=
and =header-value-relaxed= combined with nothing anywhere in the corpus.

A fourth oracle binary, =http-modes-c=, is the same parser graph built with
=tools/oracle/lenient-init.c= — an init hook of ours that reads the kind and
a flag mask from the environment. It assigns two integer fields and prints
nothing; every trace line still comes from upstream's =extra.c=, which is
what decision 0010 protects.

*It is held to upstream's own binaries rather than argued into place.* At no
flags it must equal =http-request-c= and =http-response-c=; at one flag it
must equal =http-request-lenient-headers-c=, built by upstream's harness with
none of our code.

The flag subsets *walk a fixed schedule* — 11 singletons, then all 55 pairs,
then the whole set — so the seed moves the input rather than the coverage. A
random draw over 55 pairs needs hundreds of cases, and "probably covered" is
not a coverage claim.

Half the cases *match* their malformations to the subset they were given, so
the lenient path is walked to the end; the other half draw them
independently, which is where both of this producer's first findings came
from.

* The kinds and the binaries

=request= and =response= are two modes of llhttp's message parser. =url= is
its URL sub-parser built standalone — =test/md-test.ts='s =buildURL()=, with
both exits looped back to the entry, which is the program =url.md= was
recorded from. The kind travels with each generated case and picks the binary
on llhttp's side and the machine on ours, so a url case is never asked of a
message parser.

=HTTPARSE_DIFFERENTIAL_URL_CASES=0= turns the url kind off and reproduces the
run as it was before it existed.

* One seed is not a lane

The run is the seed it is given and its *two successors*, and that is a
measurement rather than a precaution. The =@= defect above did not appear at
the default seed; it appeared at three of the five seeds tried. A lane pinned
to one seed can be silently lucky, and =unclassified=0= reads as evidence
either way.

=HTTPARSE_DIFFERENTIAL_SEED= still names the run with one number, and any
member of a sweep replays alone by being named directly.

* Running it yourself

The differential is local and opt-in, never a merge gate: llhttp's own test
harness needs Node and a C toolchain, and the evidence CI needs is already
checked in.

#+begin_src sh
git clone https://github.com/nodejs/llhttp ~/src/llhttp
cd ~/src/llhttp && git checkout v9.4.3 && npm install
cd - && cmake --preset dev -DHTTPARSE_LLHTTP_ROOT=$HOME/src/llhttp
ctest --preset pr -R differential
#+end_src

Without that variable the lane is *absent* — not skipped, not failing, not
registered at all.
