#+TITLE: chez-httparse API reference
#+OPTIONS: toc:2

The parser is a *state machine plus a binding list*. You hand it bytes; it
calls you back. It allocates nothing per byte, copies no spans, and keeps no
buffer of its own — which is why a span callback receives bounds into /your/
bytevector rather than a string.

* What to import

#+begin_src scheme
(import (generated httparse-message)   ; httparse-message-machine
        (httparse modes)               ; the mode tables, pure
        (httparse methods)             ; the method table, pure
        (httparse decisions)           ; keep-alive / needs-eof, pure
        (byte-machine runtime))        ; make-parser, parser-feed!, ...
#+end_src

=src/generated/httparse-message.sls= is a derived file, emitted from
=src/httparse/grammar.sls= and committed so that what ships is reviewable as a
diff and loadable without running a generator. It depends on
=(byte-machine runtime)= and nothing else.

=(httparse modes)= is pure and depends on nothing at all — it is llhttp's two
mode tables and the arithmetic over them. You need it only to spell the
fourth argument below; the integers are llhttp's own, so a caller that
already has one may pass it directly.

=(httparse methods)= is pure in the same way — llhttp's 47 method names and the
number it prints for each. =headers complete= reports the method as that
number; =httparse-method-name= turns it into a symbol for logging or routing
(and =httparse-method-number= goes back), so you need this only when you read
the method a parsed message reports. Like the modes, an unknown name or number
is *refused, never defaulted* — zero is =DELETE=, a real method, so a typo must
not read as one.

* Making a parser

: make-parser : CompiledMachine (Listof (List Symbol Procedure)) Any [FieldInitials] -> Parser

The third argument is a *user context* handed back to every callback. Use it
for the connection state you would otherwise close over; =#f= is fine.

The fourth is optional and is where *the modes* go — see below.

*Every REQUIRED callback must be bound.* A binding list with a hole is
refused when the parser is made, not quietly ignored. That is deliberate: a
parser that silently dropped =on-body-data= would look like a message with no
body. There are no optional callbacks: everything the parser declares, it
requires.

* Feeding bytes

: parser-feed! : Parser Bytevector Nat Nat -> ParserResult

=(parser-feed! p bv start end)= consumes the half-open range. Feed as much or
as little as you have; the parser resumes exactly where it stopped, and a
token, a header or a body split across any number of feeds produces the same
result as one whole buffer. (One exception is measured and documented in
[[file:conformance.org][conformance.org]].)

** Reading the result

| =parser-result-status=        | see below                                    |
| =parser-result-consumed=      | bytes taken from this feed                   |
| =parser-result-next=          | where to resume in this buffer (see below)   |
| =parser-result-stream-offset= | bytes taken since the parser was made        |
| =parser-result-error=         | a =ParserError= when the status is ='error=  |
| =parser-result-pause=         | the pause reason when the status is ='paused=|

Statuses:

- ='need-input= — the range is consumed; feed more. This is the ordinary
  outcome, including *after a complete message*: a connection may carry
  another one.
- ='error= — the message is malformed, *or* the HTTP/2 preface handed off on
  this channel (see *Upgrades hand off on two channels* below).
  =parser-result-error= carries the detail; for a malformation the parser makes
  no further progress.
- ='paused= — a callback returned =callback-pause=, or the parser reached a
  CONNECT/Upgrade hand-off (again, *Upgrades* below). Resume with
  =parser-resume!= and feed again from =parser-result-next=.
- ='finished= / ='stopped= — the machine reached a terminal state.

** Errors

: parser-error-code      : ParserError -> Symbol   ; e.g. 'invalid-header-token
: parser-error-reason    : ParserError -> String   ; llhttp's own text
: parser-error-offset    : ParserError -> Nat      ; stream offset
: parser-error-node-name : ParserError -> Symbol   ; the grammar node that refused

The code/reason pair is llhttp's, deliberately: decision 0013 makes an
error's identity the pair rather than either half, so a caller can switch on
the symbol and log the text and get the same answer llhttp would give.

*** Mapping a Transfer-Encoding error to a response status

Every =invalid-transfer-encoding= on a request is a =400=, and the code alone
is enough to say so. A strict parser refuses a request with that code in four
ways:

| request                                        | node                        | why a =400=       |
|------------------------------------------------+-----------------------------+-------------------|
| =Transfer-Encoding:= with an empty value       | =e-empty-transfer-encoding= | §6.3, item 4      |
| =Transfer-Encoding: chunked, deflate=          | =e-bad-te-value=            | §6.3, item 4      |
| =Transfer-Encoding: gzip=                      | =e-request-invalid-te=      | §6.3, item 4      |
| =Content-Length=, then =Transfer-Encoding=     | =e-te-with-content-length=  | §6.1, §6.3 item 3 |

The sections are RFC 9112's. In the first three rows =chunked= is not the
final coding, and §6.3 item 4 says the server "MUST respond with the 400 (Bad
Request) status code" to such a request and then close the connection. llhttp
quotes that rule at the branch that produces the third row.
=chunked, chunked= also lands at =e-bad-te-value=. Its final coding is
=chunked=, but §6.1 lets a sender apply =chunked= only once, so the message is
malformed and still a =400=. In the fourth row the request carries both
framing headers. §6.1 lets a server reject that, the parser does, and either
way the server "MUST close the connection" after answering it. The opposite
order, =Transfer-Encoding= then =Content-Length=, is refused too, but under
=invalid-content-length=.

A =501= is still possible, but the parser does not produce one. RFC 9112 §6.1
gives a SHOULD =501= for a transfer coding the server does not understand, and
the MUST in §6.3 wins wherever both apply. So §6.1 is left with the requests
the parser *accepts*: codings that end in =chunked= but list another first,
such as =gzip, chunked=. Only you know which codings you implement. If
=gzip= is not one of them, you answer that request with a =501= yourself,
from the =Transfer-Encoding= value your header callbacks collected.

*** Telling failures within one code apart

=parser-error-code= is one-to-one with llhttp's error number (decision 0013).
llhttp gives several distinct failures one number, and so do we, so those
failures share a code. Usually that is what you want. When it is not (a log
line that says /which/ Transfer-Encoding failure it was, say), do not match
on the reason string. That match breaks as soon as llhttp re-words the
reason. Match on =parser-error-node-name=, which returns the node column of
the table above. =unit.te-error-nodes= holds those four names to every strict
request fixture in the corpus that ends in this code.

=parser-error-node-name= is the *grammar's* own label for the node that
refused. It is finer than the code, which is why it can split one. But it is
our label, not llhttp's, and a node name can move where a =(code, reason)=
pair will not. So reach for it only to split within a code you have already
matched; the pair stays the stable, llhttp-faithful identity. One declaration
can also surface under several node names when it is reachable with different
spans open (end-of-input is the extreme). So a node name marks a *site*, and
is not always a one-per-failure key. For each of the four in the table above
it is one: every refusal under that reason stops at that node, which is what
=unit.te-error-nodes= checks.

** Pausing, and where to resume

A feed can stop before the end of your buffer — a callback returned
=callback-pause=, or the parser reached an upgrade hand-off (below). Either
way =parser-result-next= is *the offset in the buffer you just fed* where the
unconsumed tail begins, and it is what you feed from next. It shares the
coordinate of the =start=/=end= you passed to =parser-feed!=, so it feeds
straight back in; =parser-result-stream-offset= is the absolute count since the
parser was made, and is what you log.

The byte that stopped the parser is already behind it. At a pause,
=parser-result-consumed= *includes* the fragment delivered to the pausing
callback, and =parser-result-next= points one past it — so a resume re-enters
where an unpaused run would have gone, not at that fragment again.

#+begin_src scheme
;; Feed one buffer, honouring any pauses within it.
(let loop ((at 0))
  (let ((r (parser-feed! parser buf at (bytevector-length buf))))
    (case (parser-result-status r)
      ((paused)
       (act-on-the-pause r)          ; your reason for pausing; then continue
       (parser-resume! parser)
       (loop (parser-result-next r)))  ; the tail starts here, not at `at`
      (else r))))
#+end_src

On ='need-input= the whole buffer was taken — =next= equals your =end= and
there is nothing to re-feed, so you supply the next buffer instead.

** Upgrades hand off on two channels

When a message hands the connection to another protocol, the parser stops and
tells you — but on *two different result channels*, so a dispatch on
=parser-result-status= alone will miss one:

| Hand-off                                     | =status=  | reason from           | code                |
|----------------------------------------------+-----------+-----------------------+---------------------|
| CONNECT tunnel · =Connection: upgrade= · 101 | ='paused= | =parser-result-pause= | =paused-upgrade=    |
| HTTP/2 preface (=PRI * HTTP/2.0=)            | ='error=  | =parser-result-error= | =paused-h2-upgrade= |

The first is a pause because the parse could resume; the second is an =error=
because llhttp implements the h2 preface that way — its reason still reads
"Pause". In both, =parser-result-next= is where the tunnelled or next-protocol
bytes begin in the buffer you fed: hand that tail to whatever takes the
connection.

Because the two arrive differently, recognising a hand-off means checking both
channels:

#+begin_src scheme
;; #t when the result is either upgrade hand-off, whichever channel it took.
(define (result-hands-off-stream? r)
  (or (and (eq? (parser-result-status r) 'paused)
           (let ((p (parser-result-pause r)))
             (and p (eq? (parser-error-code p) 'paused-upgrade))))
      (and (eq? (parser-result-status r) 'error)
           (let ((e (parser-result-error r)))
             (and e (eq? (parser-error-code e) 'paused-h2-upgrade))))))
#+end_src

A plain =callback-pause= is also ='paused=, but it carries no reason
(=parser-result-pause= is =#f=), so the code check tells a hand-off from an
ordinary pause.

* Callbacks

An *event* callback is =(lambda (parser ctx) outcome)=. A *span* callback is
=(lambda (parser ctx bv from to) outcome)=, where =[from,to)= indexes the
bytevector /you/ passed to =parser-feed!=. The bytes are not copied and are
not retained: copy what you need before returning.

An outcome is =callback-continue=, =callback-pause=, or a
=make-callback-failure=.

** Where a callback is in the stream

: parser-stream-offset : Parser -> Nat

=from= and =to= place a span's bytes in the buffer you fed and say nothing
about the stream, and an event is handed no position at all. For the stream,
read =parser-stream-offset=: the bytes the parser has taken since it was
made or last reset, counted across feeds and across every message parsed on
it. Between feeds it is the number =parser-result-stream-offset= reported.
Inside a callback it says where that callback is, and the two kinds of
callback answer differently:

- *An event callback* reads the bytes taken before it. That is the position
  llhttp's traces print as ~off=~ for the event, and it is the same however
  the input was split across feeds.
- *A span callback* reads the position of its fragment's *end*, so the
  fragment starts at =(- (parser-stream-offset p) (- to from))=. That holds
  whichever feed delivered the fragment, including one cut off because a feed
  ended with the span still open, and an empty one, which starts where it
  ends.

The corpus's first request, =request/sample.md#1=, shows both, fed in one
piece (=\t= is a tab):

#+begin_example
OPTIONS /url HTTP/1.1
  on-method-data            "OPTIONS"  reads  7   it starts at 7 - 7 = 0
  on-method-complete                   reads  7   the space after OPTIONS is not yet taken
  on-url-data               "/url"     reads 12   it starts at 12 - 4 = 8
  on-url-complete                      reads 13   the space after /url is already taken
...
Header2:\t Value2
  on-header-field-complete             reads 48   the colon is taken
  on-header-value-data      "Value2"   reads 56   it starts at 56 - 6 = 50
#+end_example

So an event does not always sit where the span before it ended. Which side
of a delimiter it lands on is llhttp's choice, made event by event, and the
corpus's logs record every one. A run of bytes no callback covers lies
between one callback's position and the next one's, so its length is the
difference: the tab and the space before =Value2= are 50 - 48 = 2 bytes.
Blank lines before the first request line are the bytes taken before
=on-message-begin=. Between two messages they lie between
=on-message-complete= and the =on-reset= that follows it.
=unit.stream-offset= holds the parser to all of this over every fixture in
the corpus, feeding each chunk from a buffer of its own.

** The one callback that answers

=on-headers-complete= is a *decision*: it returns ='skip-body= or nothing.
Pausing is allowed there, because a resumed run re-enters the body decision
exactly where an unpaused one would.

It is the only one. =on-message-type= used to be the other, and is now the
=type= mode below — see *Choosing the modes*.

** The full list

| Span                             | Event                                |
|----------------------------------+--------------------------------------|
| =on-method-data=                 | =on-method-complete=                 |
| =on-url-data=                    | =on-url-complete=                    |
| =on-protocol-data=               | =on-protocol-complete=               |
| =on-version-data=                | =on-version-complete=                |
| =on-status-data=                 | =on-status-complete=                 |
| =on-header-field-data=           | =on-header-field-complete=           |
| =on-header-value-data=           | =on-header-value-complete=           |
| =on-body-data=                   |                                      |
| =on-chunk-extension-name-data=   | =on-chunk-extension-name-complete=   |
| =on-chunk-extension-value-data=  | =on-chunk-extension-value-complete=  |

Events with no span: =on-message-begin=, =on-headers-complete=,
=on-chunk-header=, =on-chunk-complete=, =on-message-complete=, =on-reset=.

That is the whole list — *twenty-five, all required*. There is no
=on-message-type= and there are no =on-lenient-*=; both are modes now.

=on-reset= fires between pipelined messages on one parser, before
=on-message-begin= of the next.

** The request target is checked, not just captured

=on-url-data= still delivers the *whole* target as one span — that has not
changed. What changed is that a target whose STRUCTURE llhttp rejects is now
an error here too, where it used to parse:

#+begin_example
OPTIONS a.com:443 HTTP/1.1
  ->  error code 7, "Unexpected char in url schema", at offset 9
#+end_example

The parser runs llhttp's own URL machine over the target, entering it at the
authority form for =CONNECT= and at the general form for everything else.
*A message you used to parse may now be refused*, with one of llhttp's
=invalid-url= reasons. No =on-url-data= fires before such an error: the span
is open when the refusal happens, and an error abandons an open span rather
than flushing it.

A target with *two userinfo =@= that are not adjacent* is accepted, because
llhttp accepts it: =http://a@b@c/p= is a host of =a@b@c=. Only =@@= is
=Double @ in url=. This parser refused the second =@= wherever it fell until
the live differential said otherwise.

If you want the target broken into schema, host, path, query and fragment,
that is the separate parser below.

* Choosing the modes

=make-parser='s fourth argument is an alist of *field initials*. Two fields
accept one, and together they are everything the parser needs to be told
before the first byte:

#+begin_src scheme
(make-parser httparse-message-machine bindings #f
             (list (cons 'type (httparse-message-type-value 'request))
                   (cons 'lenient-flags
                         (httparse-lenient-flags-value '(headers version)))))
#+end_src

Both are llhttp's own integers, written the way llhttp's embedder writes
them. The alist is *range-checked at construction* and refused for an unknown
or non-settable field name, a duplicate, or an out-of-range value — so a
misspelled mode is an error, never a silent default.

** =type= — request or response

HTTP does not say which is coming: a request begins with a method and a
response with =HTTP/=, and the embedder always knows, from which side of the
connection it is on.

: (httparse-message-type-value 'request)   ; => 1
: (httparse-message-type-value 'response)  ; => 2

*This one has no safe default.* Omit it and the parser starts at llhttp's
=HTTP_BOTH=, which this parser does not implement — llhttp's third arm sniffs
the first bytes and v0.1 does not — so the first feed returns
='unexpected-message-type= at offset 0 rather than guessing. That is a
refusal, not a fallback, but it is a refusal *one feed later* than the
missing-callback error it replaced. Decision 0021 records why that was
accepted.

** =lenient-flags= — llhttp's eleven leniencies

A bitset, strict at zero, which is the default when the row is omitted.

: (httparse-lenient-flags-value '(version optional-lf-after-cr))   ; => 80

: headers                 data-after-close
: chunked-length          optional-lf-after-cr
: keep-alive              optional-crlf-after-chunk
: transfer-encoding       optional-cr-before-lf
: version                 spaces-after-chunk-size
:                         header-value-relaxed

They correspond one-for-one to llhttp's =llhttp_set_lenient_*= functions, and
each does what that function's documentation says.

*Set once, not once per message.* The field is written at construction, and
the restart between two pipelined messages does not touch it — it stores zero
over =flags=, which is a different field for exactly this reason. It also
survives =parser-reset!=, which restores the initials *you* gave rather than
the ones the machine declares.

*Two of them are only useful together, at more than one site.*
=optional-cr-before-lf= sends a bare LF to a node that then expects the LF it
has just consumed, so =optional-lf-after-cr= is needed as well — at a chunk
size, and at a *request line*:

#+begin_example
PUT / HTTP/1.1\nHost: x\n\n
  with optional-cr-before-lf alone
    ->  error code 2, "Expected CRLF after version", at offset 15
  with both
    ->  parses
#+end_example

Note the *code*: strict gives the same reason and offset with code 9, so the
reason text alone cannot tell the three apart. That is upstream's behaviour,
reproduced.

*One of them stands alone where you might expect a pair.* A response status
line with *no reason phrase* ending in a bare LF — =HTTP/1.1 200\n= — is
completed by =optional-cr-before-lf= by itself, because upstream's arm there
goes straight to the completion rather than to a node wanting the LF again.
The two sites read alike and behave differently.

* The url sub-parser

A SECOND, SEPARATE PARSER, for callers that want a request target broken into
its parts. It is llhttp's own URL machine in the build its =url= fixtures were
recorded from, and it is not used by the message parser above — that one
carries the whole target as a single =on-url-data= span.

#+begin_src scheme
(import (generated httparse-url)        ; httparse-url-machine
        (byte-machine runtime))
#+end_src

Five span callbacks, all required, and *no events at all*:

: on-url-schema-data     on-url-query-data
: on-url-host-data       on-url-fragment-data
: on-url-path-data

There is no mode: =make-parser= takes its three arguments and no field
initials, because the machine declares no settable field.

** What it does not split

=on-url-host-data= carries the *whole* authority — userinfo, host and port
together, brackets and all. =http://a:b@host.com:8080/p= gives one host span,
="a:b@host.com:8080"=. llhttp does not separate them and neither does this.

** Two edges worth knowing

*A space, CR or LF ends the URL and STARTS ANOTHER.* That is the build
llhttp's url fixtures run against — its two exits are looped back to its own
entry — so =/path /next= produces two path spans, and what follows a space is
judged from scratch (=http://host.com xyz= reports =xyz= as a *schema*). If
you feed it one URL at a time, you will not meet this.

*A host that ends at a =?= keeps the =?=.* =http://host.com?q=1= gives
=span[url.host]="host.com?"=. That is upstream's behaviour, measured rather
than inferred, and reproduced rather than repaired.

* Reading parser state

: parser-field-ref : Parser Symbol -> Nat

| ='method=         | llhttp's method number, not an index into any list here |
| ='status-code=    | a response's three digits                               |
| ='http-major=     |                                                         |
| ='http-minor=     |                                                         |
| ='flags=          | llhttp's flag bits                                      |
| ='content-length= | *what remains to be read*, not what was declared        |
| ='upgrade=        | 1 if this message upgrades, as =llhttp_get_upgrade=     |

=content-length= counts *down* as the body arrives, which is llhttp's own
behaviour. Read it inside =on-headers-complete= if you want the declared
length; by =on-message-complete= it is zero.

** Does this message upgrade?

=upgrade= is llhttp's own answer, so you need not copy its rule. It is 1 when
the message carries both an =Upgrade= header and =Connection: upgrade= *and*
is a request or a =101= response, or when it is a =CONNECT= request;
otherwise 0. A response that sends both headers under any other status is only
announcing support, and reads 0.

*Read it in =on-headers-complete= or later in the same message.* It is written
once, just before that callback runs, and then holds through the body,
=on-message-complete= and the hand-off result. It is *not* cleared between
messages, so before the next =on-headers-complete= it still holds the previous
message's answer — after a =CONNECT= and a resume, the next message's
=on-message-begin= reads 1. =parser-reset!= returns it to 0.

#+begin_src scheme
(list 'on-headers-complete
      (lambda (p ctx)
        (when (= 1 (parser-field-ref p 'upgrade))
          (plan-to-close-after-this-message ctx))  ; e.g. serve, then hand off
        callback-continue))
#+end_src

The field and the hand-off result are separate answers. A =101= always hands
off (='paused=, =paused-upgrade=), but without the two headers its =upgrade=
is 0. llhttp also lets =on_headers_complete= return 2 to force an upgrade;
this parser's callback has no such answer, so =upgrade= is only ever llhttp's
computed rule. =unit.upgrade-field= holds it to that rule over every plain
request and response fixture in the corpus.

** Deciding keep-alive vs close

=(httparse decisions)= is pure and turns those fields into llhttp's own two
after-a-message decisions:

: should-keep-alive? : Nat Nat Symbol Nat Nat -> Boolean  ; major minor type status-code flags
: message-needs-eof? : Symbol Nat Nat -> Boolean          ; type status-code flags

They mirror =llhttp_should_keep_alive= and =llhttp_message_needs_eof=
exactly. =should-keep-alive?= is the version/=Connection= gate *and* not
needing eof, so it takes both the version and =message-needs-eof?='s inputs;
the version test is llhttp's literal =major > 0 && minor > 0=, so HTTP/2.0
(minor 0) needs an explicit =keep-alive= where a naïve =>= 1.1= would not.

*Read the flags inside =on-headers-complete= or =on-message-complete=*, and
pass the =type= symbol you gave =make-parser= — the inter-message reset zeroes
=flags= before the next message. The library also exports the =F-*= flag bits
(=F-CONNECTION-CLOSE=, =F-SKIP-BODY=, …) under llhttp's names and values, so
you can name a bit rather than hard-code =2=; the grammar imports the same
definitions. An unknown =type= is *refused, never defaulted*.

#+begin_src scheme
(list 'on-message-complete
      (lambda (p ctx)
        (define keep?
          (should-keep-alive? (parser-field-ref p 'http-major)
                              (parser-field-ref p 'http-minor)
                              response-or-request        ; the symbol you passed
                              (parser-field-ref p 'status-code)
                              (parser-field-ref p 'flags)))
        (remember-keep-alive ctx keep?)
        callback-continue))
#+end_src

* Lifecycle

: parser-reset!  : Parser -> unspecified
: parser-resume! : Parser -> Symbol
: parser-finish! : Parser -> ParserResult

=parser-reset!= returns the parser to its just-constructed state, fields
included — restored to the initials it was *built with*: yours for the two
modes above, the machine's declared ones for everything else. Not to zero,
and not back to the machine's defaults.

=parser-resume!= changes the lifecycle only: no callback runs, no input is
read, and it returns an acknowledgement symbol rather than a result. Feed or
finish again afterwards.

=parser-finish!= says the input has ended and asks whether stopping here is
legal. It runs the machine with input exhausted, taking each state's
end-of-input route, and returns ='finished=, ='error= or ='paused=.

*The corpus never calls =parser-finish!=* — upstream's harness does not
either, which took four milestones to notice — so a finish's outcome carries
no bit-exact /corpus/ evidence, and =unit.finish= pins it instead: a finish
from an unsafe (mid-message) state is llhttp's =invalid-eof-state= /
"Invalid EOF state" (code 14), uniform across every such state, and a
close-delimited body completes (below). A PAUSE FROM A FEED IS DIFFERENT: 24
fixtures record one, and this parser matches all of them at every chunk size.
See [[file:conformance.org][conformance.org]].

A body the *connection* delimits is the one message that completes at
=parser-finish!= and nowhere else: its body runs to the close, so no feed can
end it. That is a response with neither =Content-Length= nor
=Transfer-Encoding= (the =message-needs-eof?= case above), a response whose
=Transfer-Encoding= does not end in =chunked=, and such a request under the
=transfer-encoding= or =chunked-length= lenient flag. =on-message-complete=
fires on that finish, mirroring llhttp's =llhttp_finish= for a =SAFE_WITH_CB=
body, and a pause or failure that callback returns is what the finish result
carries.

It is the only callback the finish runs. The body's bytes arrive with the
feeds that carried them, which is where llhttp delivers them too, so by the
finish every one has been through =on-body-data=. A body that got no bytes
gets no =on-body-data= at all, not an empty one at the finish; llhttp's
=on_body= does not fire for it either. This is the single
=on-message-complete= the corpus cannot reach — it never finishes — so
[[file:../test/common/finish-tests.sps][test/common/finish-tests.sps]] is its test.
