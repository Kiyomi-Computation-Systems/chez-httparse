* chez-httparse

(CI badge goes here)

An HTTP/1.x parser for Chez Scheme, built as a byte-level state machine and
measured against [[https://github.com/nodejs/llhttp][llhttp]]'s own conformance corpus — not by re-implementing
its tests, but by replaying llhttp's *recorded traces* and comparing byte for
byte, at every chunk size.

#+begin_quote
✨ *AI Disclosure:* LLMs are used extensively in the planning and development of this project.
#+end_quote

*Status: v0.4.3.* Request and response parsing, strict and lenient: *all 274*
fixtures in llhttp's conformance corpus — every HTTP fixture and every URL
fixture it ships — at every chunk size from 1 to the input length, with an
empty deferral list. The URL fixtures are a second generated parser, for the
five spans llhttp's own url binary reports. A live differential against a built
llhttp agrees on 9,557 generated inputs besides. See
[[file:docs/conformance.org][docs/conformance.org]].

v0.4.3 moves the byte-machine pin to =v0.6.1=, whose keyword walk no longer
copies the prefix it has matched on every byte. A header name's cost no longer
depends on how much of =Transfer-Encoding= (or any name the parser reads by
name) it happens to match, and a lane asserts that shape. A small POST allocates
less than half what it did, and a whole-buffer parse is 35–80% faster. The
shipped parser is byte-identical to v0.4.2. See
[[file:docs/performance.org][docs/performance.org]].

v0.4.2 corrects how =docs/api.org= maps a Transfer-Encoding error to a response
status. Every request failure under =invalid-transfer-encoding= is a =400=
(RFC 9112 §6.3), not the =501= the note gave for one of them. The four node
names that tell those failures apart are now pinned by a lane. The shipped
parser is byte-identical to v0.4.1.

v0.4.1 documents the =upgrade= field as llhttp's =llhttp_get_upgrade=, with
when it is valid, and pins it with a lane over the corpus. The shipped parser
is byte-identical to v0.4.0.

v0.4.0 aligns the =parser-finish!= path with llhttp on the two points the
corpus cannot reach. A close-delimited response body now fires
=on-message-complete= when the embedder finishes the parse, and a finish from a
half-read message reports llhttp's =invalid-eof-state= / "Invalid EOF state" in
place of an error of our own. Conformance holds at 274/274 — no fixture
finishes — but the shipped parser is no longer byte-identical: v0.3.0's
additions did not touch it, these do (a node added, an error renamed). The
release also documents the result surfaces a connection layer reads at a pause
or an upgrade hand-off, and how =parser-error-node-name= splits one error code
across two response statuses.

v0.3.0 adds two pure, runtime-safe libraries for embedders, lifted out of the
build-time grammar: =(httparse methods)= (llhttp's method name/number tables)
and =(httparse decisions)= (its keep-alive / needs-eof rules and the flag bits
they read). Additive — conformance and performance are unchanged, and the
shipped parser is byte-identical.

v0.1 shipped 190 fixtures, strict-mode only, and parsed a 308-byte request at
14,925 msg/s; v0.2 parses the same request at *175,000*. None of that twelvefold
is in this repository — it is four dispatch fixes in the generator, and
[[file:docs/performance.org][docs/performance.org]] records them, the ratios
against llhttp (25.5× on its own bench input, from 485×), and what wrapping
llhttp through the FFI would actually buy.

* What it is

- *A state machine, not a reader.* You feed it bytes; it calls you back. It
  keeps no buffer of its own, copies no spans, and allocates nothing in
  proportion to the input — a 10 KB body costs what a 10-byte one does.
- *Resumable by construction.* A token, header or body split across any
  number of feeds parses identically to one whole buffer. That is what the
  corpus replay at every chunk size actually tests.
- *Generated and committed.* =src/generated/httparse-message.sls= is emitted
  from =src/httparse/grammar.sls= and checked in, so what ships is reviewable
  as a diff and loadable without running a generator. A reference
  interpreter runs beside it over every fixture and must agree.
- *Pure Scheme.* No C, no FFI. The only dependency is the state-machine
  generator's runtime library.

* Using it

#+begin_src scheme
(import (generated httparse-message)
        (httparse modes)
        (byte-machine runtime))

(define parser
  (make-parser
   httparse-message-machine
   (list
    ;; A span callback gets bounds into YOUR bytevector. Nothing is copied
    ;; and nothing is retained -- take what you need before returning.
    (list 'on-method-data
          (lambda (p ctx bv from to) (remember-method bv from to) callback-continue))
    (list 'on-header-field-data
          (lambda (p ctx bv from to) (remember-field bv from to) callback-continue))

    ;; ... the remaining callbacks. Every declared one must be bound: a
    ;; binding list with a hole is refused when the parser is made, not
    ;; quietly ignored.
    )
   #f
   ;; The mode, chosen before the first byte. Nothing in the bytes says
   ;; whether a request or a response is coming, and the embedder always
   ;; knows; the second row is llhttp's lenient bitset, and omitting it
   ;; parses strictly.
   (list (cons 'type (httparse-message-type-value 'request))
         (cons 'lenient-flags (httparse-lenient-flags-value '())))))

(let ((r (parser-feed! parser chunk 0 (bytevector-length chunk))))
  (case (parser-result-status r)
    ((need-input) 'feed-more)
    ((error) (parser-error-reason (parser-result-error r)))
    (else (parser-result-status r))))
#+end_src

*The complete runnable version of this example is
[[file:test/common/example-tests.sps][test/common/example-tests.sps]]*, which runs in CI — so it cannot drift from
what the library actually does. [[file:docs/api.org][docs/api.org]] is the reference.

* Requirements

- Chez Scheme 10.4.1 or newer (=scheme=, =chez= and =chezscheme= are all
  probed; Petite is rejected)
- CMake 3.26 or newer (4.3.3 is what has actually been exercised)

The CMake-layer specifications run with no Scheme installed, via the
=no-scheme= preset. The optional live-llhttp differential additionally needs
Node and a C toolchain; it is off unless you ask for it.

* Portability

The libraries are *pure R6RS*. Nothing under =src/= imports =(chezscheme)=: the
grammars import =(rnrs)= and =(byte-machine graph)=, and both generated artifacts
import =(rnrs)= and =(byte-machine runtime)= and nothing else. The same holds for
byte-machine's own =src/=. Porting to Guile, Racket or another R6RS system is
therefore a *tooling* job, not a library one.

Chez appears in four places, all of them build- or test-time:

- the test harness — =(only (chezscheme) machine-type scheme-version getenv
  system statistics sstats-bytes real-time with-output-to-string
  display-condition)=, eight names enumerated rather than a blanket import
- =tools/emit-machine.ss= — command-line arguments, file output, =exit=
- byte-machine's bench runner — timing, allocation, and =compile-file= for the
  ahead-of-time lane
- =cmake/HttparseChez.cmake= — probing for the executable

Most of those eight have a direct equivalent or a short replacement. The
exception is =statistics= / =sstats-bytes=, which back the allocation lane:
allocation accounting has no portable spelling, so that lane is Chez-only by
construction and a port would reimplement or drop it.

Two things to expect. Library resolution differs — Racket wants =#lang r6rs=
wrapping, Guile has its own search rules — and the generated parser is a large
mutually-recursive set of internal definitions leaning on proper tail calls, a
shape Chez compiles particularly well; the figures in
[[file:docs/performance.org][docs/performance.org]] are Chez's and would need
re-measuring.

Every Scheme lane in the build already takes a =BACKEND= argument
(=cmake/HttparseSchemeLane.cmake=), with =chez= as the only value it knows. That
is where a second runtime attaches.

*None of this has been tried.* The library is portable by construction, not by
measurement — and this project does not claim a property it has not measured.

* Building and testing

Run =make= (or =make help=) for the full target list. The main entries:

| =make build=    | configure and build the development preset      |
| =make dev=      | build, then run the harness self-tests          |
| =make test=     | build, then run the pull-request selection      |
| =make test-all= | build, then run the complete selection          |
| =make clean=    | remove all build trees                          |

Every target is a thin wrapper over checked-in CMake presets, so
=cmake --preset dev= and =ctest --preset pr= work identically everywhere,
including on Windows where =make= is not in the base install.

To run the parser against a live llhttp on generated input, see
[[file:docs/conformance.org][docs/conformance.org]].
